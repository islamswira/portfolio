Scalable Network Layer in SwiftUI with Clean Architecture

Networking is one of the most critical parts of any modern iOS application. Whether you’re building a fintech app, a social platform, or an SDK consumed by multiple apps, a poorly designed network layer quickly becomes a bottleneck. With SwiftUI and modern iOS architectures, it’s no longer enough to “just make API calls.” We need a clean, testable, scalable, and reusable network layer that fits naturally within Clean Architecture. In this article, I’ll walk through how to design a robust network layer in SwiftUI, aligned with Clean Architecture principles, and explain why each decision matters

Why Networking Becomes a Bottleneck at Scale

Early-stage apps often place networking logic directly inside ViewModels. This works — until the app grows.

  • ViewModels become aware of HTTP concepts
  • Error handling is duplicated across screens
  • Mocking requires fragile hacks
  • SDK reuse becomes impossible

Clean Architecture forces us to treat networking as an infrastructure detail, not a feature concern.

Where the Network Layer Lives in Clean Architecture

The network layer belongs to the outermost circle. It depends inward — never outward.

That means:

  • No SwiftUI imports
  • No ViewModels
  • No business rules

Its only job: transport + decoding.

Designing a Protocol-Driven Network Client

protocol NetworkClient {
    func send<T: Decodable>(
        _ request: URLRequest
    ) async throws -> T
}

This abstraction gives you:

  • Replaceable implementations
  • Deterministic tests
  • SDK-ready architecture

URLSession as an Implementation Detail

final class URLSessionNetworkClient: NetworkClient {

    func send<T: Decodable>(
        _ request: URLRequest
    ) async throws -> T {

        let (data, response) =
            try await URLSession.shared.data(for: request)

        guard let httpResponse = response as? HTTPURLResponse,
              200...299 ~= httpResponse.statusCode else {
            throw NetworkError.invalidResponse
        }

        return try JSONDecoder().decode(T.self, from: data)
    }
}

Note how this class has:

  • No knowledge of endpoints
  • No domain awareness
  • No UI dependencies

Endpoint Abstraction (Avoiding Stringly-Typed APIs)

protocol Endpoint {
    var path: String { get }
    var method: HTTPMethod { get }
    var headers: [String: String] { get }
}

This allows compile-time safety and consistency across requests.

Decoding Is Not Domain Modeling

struct UserDTO: Decodable {
    let id: String
    let name: String
}

struct User {
    let id: String
    let displayName: String
}

extension User {
    init(dto: UserDTO) {
        id = dto.id
        displayName = dto.name
    }
}

DTOs mirror the API. Domain models mirror the business. They should evolve independently.

Threading & SwiftUI Integration

@MainActor
final class UsersViewModel: ObservableObject {

    @Published var users: [User] = []

    private let client: NetworkClient

    init(client: NetworkClient) {
        self.client = client
    }

    func loadUsers() async {
        let dtos: [UserDTO] =
            try await client.send(
                UsersEndpoint()
                    .makeRequest(baseURL: API.baseURL)
            )

        users = dtos.map(User.init)
    }
}

Notice how:

  • Concurrency stays explicit
  • ViewModels stay testable
  • No networking logic leaks upward

Error Modeling for Real Systems

enum NetworkError: Error {
    case invalidResponse
    case unauthorized
    case decoding(Error)
    case transport(Error)
}

Explicit error modeling is essential for:

  • Analytics
  • User messaging
  • Retry strategies

Testing Without the Network

final class MockNetworkClient: NetworkClient {

    func send<T: Decodable>(
        _ request: URLRequest
    ) async throws -> T {
        try MockData.load()
    }
}

This allows full ViewModel testing with:

  • No HTTP calls
  • No async flakiness
  • Predictable results

Key Takeaways for Senior Engineers

  • Networking is infrastructure, not feature logic
  • Protocols unlock testability and reuse
  • DTOs and domain models must be separated
  • Design for SDKs even if you don’t ship one yet
