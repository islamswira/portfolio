From @StateObject & @ObservedObject to Swift Observation

SwiftUI's state management story has evolved dramatically: from UIKit view controllers, to ObservableObject, and now to the new @Observable macro and Observation framework. In this article we'll walk through where state used to live, what the older patterns cost us, and how the new Observation system makes things simpler and safer.

At a glance: from UIKit controllers to @Observable

If you step back and look at the last few years of iOS development, state management has moved through three big phases: imperative UIKit controllers, Combine-based ObservableObject, and now language-level Observation.

State over the years UIKit → SwiftUI → Observation
UIKit controllers
ObservableObject + @StateObject
@Observable model
  • UIKit era: view controllers owning and mutating all the state.
  • SwiftUI 1.0: ObservableObject + @Published wrapped in @StateObject / @ObservedObject.
  • Observation: one @Observable model, with fine-grained dependency tracking and better performance.

The rest of this article drills into each of these phases, but this hero section is the mental picture you can keep in your head while you read.

Before SwiftUI: Where Did View State Live?

Long before SwiftUI and @StateObject, most iOS apps were built using UIKit and the classic MVC pattern. View state and domain state were often mixed together inside UIViewController subclasses or custom views.

Typical patterns looked like this:

  • View controllers as "massive" state containers – properties on UIViewController for everything: form fields, loading flags, error messages, and derived values.
  • Delegates and callbacks – views communicated upwards using delegate protocols or closures, and the controller pushed state changes back down.
  • KVO & notifications – for cross-screen or cross-layer updates, teams used KVO or NotificationCenter, which were powerful but fragile and hard to reason about.

This worked, but it had serious drawbacks:

  • State was spread across controllers, models, and global singletons.
  • It was hard to know who owned a piece of state and who could mutate it.
  • UI updates were usually manual – calling tableView.reloadData(), setNeedsLayout(), or pushing view controller transitions at the right time.

SwiftUI's promise was: describe your UI as a pure function of state, and let the framework handle updates automatically. But we still needed a way to model that state.

The SwiftUI 1.0 Model: ObservableObject, @StateObject & @ObservedObject

When SwiftUI first arrived, the main pattern for shared or long-lived state was ObservableObject plus a couple of property wrappers:

  • @State – simple local value type state owned by the view.
  • ObservableObject – a reference type that publishes changes via @Published.
  • @ObservedObject – a view depends on an ObservableObject it does not own.
  • @StateObject – a view creates and owns its ObservableObject.
  • @EnvironmentObject – a shared ObservableObject injected via the environment.

A typical view model looked like this: 

final class ProfileViewModel: ObservableObject {
    @Published var name: String = ""
    @Published var isLoading: Bool = false
    @Published var errorMessage: String?

    func load() {
        isLoading = true
        // Fetch, then update properties...
    }
}

And the SwiftUI view would depend on it using @StateObject or @ObservedObject: 

struct ProfileView: View {
    @StateObject private var viewModel = ProfileViewModel()

    var body: some View {
        VStack {
            if viewModel.isLoading {
                ProgressView()
            } else {
                TextField("Name", text: $viewModel.name)
            }
        }
        .task { await viewModel.load() }
    }
}

This was already a big step forward compared to UIKit: SwiftUI automatically re-rendered the view when published properties changed. But the pattern also came with cost.

Pain Points With ObservableObject-Based State

After a few years of building real apps with ObservableObject, some common issues kept showing up:

  • Boilerplate and indirection – you often had a model type and a view model type, even when their properties were almost identical.
  • Reference types everywhere – ObservableObject forces you into class-based models, even when a simple value type would be enough.
  • Lifetime rules are easy to get wrong – choosing between @StateObject, @ObservedObject, and @EnvironmentObject confused many teams, especially early in a project.
  • Testing and previews – setting up view models and injecting them in the right way adds extra ceremony for simple UIs.

The Swift team's answer in iOS 17 was to take a step back and rethink observation at the language level, not just as a framework protocol.

Enter the Observation Framework and @Observable

The new Observation framework introduces a different mental model: instead of making your types conform to ObservableObject and annotating each property with @Published, you annotate the type itself with @Observable. Swift then automatically tracks which properties are read inside a view and re-renders that view when those properties change. 

import Observation

@Observable
final class ProfileModel {
    var name: String = ""
    var isLoading: Bool = false
    var errorMessage: String?
}

There is no explicit @Published, and you don't need the ObservableObject protocol anymore. The type can be a class, a struct, or even an actor – the macro generates the observation machinery behind the scenes.

In the view, you access it via @State, @Environment, or the new @Bindable wrapper: 

struct ProfileView: View {
    @State private var model = ProfileModel()

    var body: some View {
        VStack {
            if model.isLoading {
                ProgressView()
            } else {
                TextField("Name", text: $model.name)
            }
        }
        .task { await load() }
    }

    func load() async {
        model.isLoading = true
        // Fetch data and update model.name / model.errorMessage...
        model.isLoading = false
    }
}

Notice that we're working directly with a single model object. There is no separate view model that only exists to bridge between state and the UI.

Automatic dependency tracking

One of the biggest differences compared to ObservableObject is how SwiftUI decides when to re-render a view. With the Observation framework, Swift tracks which properties are actually read inside a view’s body and only invalidates that view when those specific properties change. 

struct GreetingView: View {
    @State private var model = ProfileModel()

    var body: some View {
        // Swift tracks a dependency on model.name here
        Text("Hello, \(model.name)")
            .font(.headline)
    }
}

If some other part of your code changes model.isLoading or model.errorMessage, GreetingView will not be recomputed, because it never read those properties. But changing model.name will invalidate the view. This property-level dependency tracking is a key reason why Observation can be more efficient and predictable than the old broadcasting model based on @Published.

Value types, classes and even actors

Another important difference is that @Observable works with more than just classes. You can annotate a reference type, a value type or even an actor, and the Observation framework will still track changes correctly. 

// Observable class
@Observable
final class ProfileModel {
    var name: String = ""
    var isLoading: Bool = false
}

// Observable struct
@Observable
struct SettingsModel {
    var isDarkModeEnabled = false
    var sendNotifications = true
}

// Observable actor (for concurrency-sensitive state)
@Observable
actor UserSession {
    var token: String?
    var isAuthenticated: Bool { token != nil }

    func updateToken(_ newToken: String?) {
        token = newToken
    }
}

With ObservableObject you were effectively forced into class-based models. The Observation framework lets you pick the right tool for each feature while still getting automatic UI updates when those models change.

Because Observation does property-level tracking instead of broadcasting every change, it can also be more performant: views only re-render when the data they actually depend on has changed, which reduces unnecessary work in complex hierarchies.

Using @Bindable for Two-Way Bindings

When you pass observable models deeper into your view hierarchy, you often want child views to both read and write to them. Instead of exposing bindings for each property, you can wrap the entire observable type in @Bindable: 

struct ProfileForm: View {
    @Bindable var model: ProfileModel

    var body: some View {
        Form {
            TextField("Name", text: $model.name)
            Toggle("Loading", isOn: $model.isLoading)
        }
    }
}

The @Bindable wrapper exposes bindings for every observable property on ProfileModel, which keeps the call site clean: 

struct ProfileView: View {
    @State private var model = ProfileModel()

    var body: some View {
        ProfileForm(model: model)
    }
}

SwiftUI automatically tracks which properties the child view reads and updates only the necessary parts of the hierarchy when those properties change.

Before vs After: Migrating a Real View Model

Let's look at a slightly more realistic example and migrate it step by step.

Old: ObservableObject-based view model 

final class CounterViewModel: ObservableObject {
    @Published var count: Int = 0
    @Published var isBusy: Bool = false

    func increment() {
        guard !isBusy else { return }
        isBusy = true
        count += 1
        isBusy = false
    }
}

New: @Observable model 

@Observable
final class CounterModel {
    var count: Int = 0
    var isBusy: Bool = false

    func increment() {
        guard !isBusy else { return }
        isBusy = true
        count += 1
        isBusy = false
    }
}

The view becomes simpler as well: 

struct CounterView: View {
    @State private var model = CounterModel()

    var body: some View {
        VStack(spacing: 16) {
            Text("Count: \(model.count)")
                .font(.largeTitle)

            Button("Increment") {
                model.increment()
            }
            .disabled(model.isBusy)
        }
    }
}

No @StateObject, no @ObservedObject, and no @Published boilerplate. You work with plain properties on a single model and let the Observation framework handle the rest.

Do We Still Need @StateObject and @ObservedObject?

The new Observation APIs don't make the old ones disappear overnight. There are cases where you may still want ObservableObject:

  • You're targeting OS versions earlier than iOS 17 / macOS 14 and can't rely on the Observation framework everywhere.
  • You have an existing architecture heavily invested in ObservableObject and mixing both styles would add confusion.
  • You're using third-party libraries that still expose ObservableObject-based types.

That said, for new code bases targeting modern OS versions, starting with @Observable models and @Bindable views is usually the most future-proof choice.

A Practical Migration Strategy

You don't need a "big bang" rewrite to adopt the Observation framework. A safe migration strategy looks like this:

  1. Keep your public API stable – start by rewriting internal view models as @Observable types, but keep their public surface the same so views don't need to change immediately.
  2. Adopt @Observable for new features – any new screen or module can start directly with Observation-based models.
  3. Introduce @Bindable in leaf views – when a view needs to edit a model, prefer passing the observable type via @Bindable instead of routing many individual bindings.
  4. Gradually remove legacy glue – once most of the app uses Observation, you can start deleting old ObservableObject wrappers and @Published properties that no longer add value.

Over time you end up with a simpler mental model: each feature has a small set of observable models, views declare which models they depend on, and Swift takes care of refreshing the right parts of the hierarchy.

Wrap Up

The Observation framework is more than a new property wrapper – it's a new way of thinking about how SwiftUI tracks changes in your app. Instead of plumbing observable objects and publishers through your views, you work with plain models annotated with @Observable and let Swift handle the observation details.

If you're starting a new SwiftUI project on modern OS versions, it's worth designing your architecture around Observation from day one. And if you're maintaining a large existing code base, you can still adopt it gradually, one feature at a time.
