Using .redacted(reason: .placeholder) for SwiftUI Skeleton States

Loading states are one of those small details that make an app feel “product ready” instead of just “it works”. In this article I’ll walk through how .redacted(reason: .placeholder) solves the classic skeleton view problem in SwiftUI, what we used to do before it existed, and a clean pattern you can plug into real projects.

Before & After .redacted(.placeholder)

The same SwiftUI view: first shown as a loading skeleton, then revealed after applying .redacted(reason: .placeholder).

Before .redacted: manual skeleton views

Before .redacted was introduced, most teams implemented loading skeletons in one of two ways:

  • Dedicated skeleton views – creating a separate ArticleRowSkeleton that mimics the layout using gray rectangles, and switching to it when isLoading == true.
  • Large conditional blocks in the body – checking loading state inside the view and returning either placeholders or the real content.

Both approaches work, but they come with a cost: duplicated layout, more code to maintain, and a higher chance that the skeleton stops matching the final design after a few refactors. 

// Old approach – two separate views
if isLoading {
    ArticleRowSkeleton()
} else {
    ArticleRow(article: article)
}

What .redacted(reason: .placeholder) gives you

The .redacted modifier lets any SwiftUI view behave like a skeleton view without creating a separate skeleton component. You write the layout once, and SwiftUI draws placeholder shapes (gray bars, boxes, etc.) in place of the original content.

The key benefit is zero layout duplication. You keep a single source of truth for your UI, and toggle the loading state using a simple boolean or a property from your view model.

A simple pattern using a loading flag

A common pattern is to let the same row component handle both loading and loaded states using a single flag: 

struct ArticleRow: View {
    let title: String?
    let summary: String?
    let isLoading: Bool

    var body: some View {
        VStack(alignment: .leading, spacing: 6) {
            Text(title ?? " ")
                .font(.headline)

            Text(summary ?? " ")
                .font(.subheadline)
                .foregroundColor(.secondary)
        }
        .redacted(reason: isLoading ? .placeholder : [])
        .animation(.easeInOut(duration: 0.25), value: isLoading)
    }
}

Here we pass a single space " " as a fallback instead of nil. That allows SwiftUI to keep the correct layout even while the content is redacted. Once isLoading flips to false, the placeholder is removed and the real content appears in exactly the same space.

Applying redaction at list level

In a real app, the loading state usually lives in a view model (for example, an @StateObject or @ObservedObject). You can apply .redacted either to individual rows or to the entire list: 

struct ArticlesListView: View {
    @StateObject private var viewModel = ArticlesViewModel()

    var body: some View {
        List(viewModel.articles) { article in
            ArticleRow(
                title: article.title,
                summary: article.summary,
                isLoading: viewModel.isLoading
            )
        }
        .redacted(reason: viewModel.isLoading ? .placeholder : [])
        .animation(.easeInOut(duration: 0.25), value: viewModel.isLoading)
        .task {
            await viewModel.loadArticles()
        }
    }
}

Applying the modifier on the list level is useful when you have multiple row types or sections and you want all of them to appear as placeholders while data is loading.

Controlling where redaction stops

Sometimes you want parts of the UI to remain real even while the rest of the view is redacted. A common example is persistent icons like a bookmark or a status badge. In those cases, .unredacted() lets you explicitly opt out: 

HStack {
    VStack(alignment: .leading) {
        Text(title ?? " ")
            .font(.headline)
        Text(summary ?? " ")
            .font(.subheadline)
    }

    Spacer()

    // Keep the bookmark icon visible even in loading state
    Image(systemName: "bookmark")
        .unredacted()
}

This helps keep key actions or visual anchors visible while still giving the user a clear loading state for the main content.

Accessibility and UX considerations

Skeleton states also need to work well with VoiceOver and other assistive technologies. You usually don’t want the screen reader to read out placeholder text, so it’s better to expose a higher-level label while the view is loading: 

VStack {
    ArticleRow(title: title,
               summary: summary,
               isLoading: isLoading)
}
.accessibilityElement(children: .ignore)
.accessibilityLabel(isLoading
    ? "Loading article..."
    : (title ?? "Article"))

Also keep the animation subtle (around 0.2–0.3 seconds) so the transition between loading and loaded feels smooth without being distracting.

When .redacted is not the right tool

Not every loading state needs a skeleton. For very fast requests or simple views, a standard ProgressView or a direct content update can be clearer. Avoid redacting controls that the user still needs to interact with while other parts of the screen are loading.

Key takeaways

  • Write the layout once and use .redacted(reason: .placeholder) instead of duplicating views for skeleton states.
  • Drive redaction from your view model using an isLoading flag or a similar piece of state.
  • Think about UX and accessibility – skeletons should make the interface clearer, not noisier, especially for screen reader users.
